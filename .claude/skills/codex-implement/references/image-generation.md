# Codex CLIによる画像生成・編集の実践ガイド

この文書は、`/codex-implement` からCodex CLIへ画像生成・編集を委任するAI向けの参考資料である。

タスク仕様書には、ユーザーが必要とする成果物、入力画像、変更点、保持条件、保存先、検収条件を記載する。
画像生成プロンプトの細部はCodexに委ねてよいが、ユーザーの必須条件を省略・変更してはならない。

本文では、次の区分を使用する。

- **[公式/API]**: 指定したモデル・APIについて公式資料で確認した仕様
- **[CLI実測]**: 記載したCLIバージョン・OS・認証方式で確認した挙動
- **[推奨]**: タスク指示や検収のための実務上の推奨事項
- **[未検証]**: 当該利用経路では確認していない事項

APIで利用できる設定が、Codex CLI内部の画像生成ツールや本リポジトリのwrapperからも指定できるとは限らない。
指定できるかどうかは、実行環境のツール仕様 (後述) で確認する。

- **正本 (SSoT)**: `docs/references/image-generation.md`。skill 同梱コピー
  (`.claude/skills/codex-implement/references/`、`.agents/skills/codex-implement/references/`)
  は `tools/sync-skill-scripts` が配布する複製であり、直接編集しない
- **公式仕様の確認日**: 2026-09-19 (developers.openai.com の Image generation guide / Image prompting guide)
- **CLI実測日**: 2026-09-19 (codex-cli 0.154.0、Windows 11 ネイティブ、ChatGPT アカウント認証) および
  2026-07-10 (codex-cli 0.144.0、Windows 11 ネイティブ、ChatGPT アカウント認証、旧記録として保持)

## 1. モデルと利用経路

[公式/API] GPT Image 2.5には、速度を重視する `gpt-image-2.5-flare` と、品質・編集精度を重視する
`gpt-image-2.5-sunburst` がある。両モデルとも生成・編集・透明背景に対応する。

[推奨] Codex CLI内部で使われる画像生成モデルは、実際に取得できる情報だけを記録する。モデル名が
公開されていない場合は「取得不可」とし、生成結果の見た目やCodexの推測によって補わない。

wrapperの `-Model` で指定するCodex側 (テキスト) のモデルと、画像生成ツールが使う画像モデルは
別のものとして扱う。`-Model` を変更すれば画像モデルも切り替わるとは仮定しない。

モデル、品質、サイズ、背景、出力形式を直接指定できるかは、実行環境のツール仕様で確認する。
未公開の引数を作ったり、自然文で希望を伝えただけで設定が適用されたと報告したりしない。

### Codex CLI 内部ツールの仕様 [CLI実測 2026-09-19、codex-cli 0.154.0]

- `codex features list` は `image_generation  stable  true` (および `view_image stable true`) を示す
- 内部 tool は `image_gen.imagegen`。ツール定義のパラメータは次の3つのみ:
  - `prompt` (string、必須)
  - `referenced_image_paths` (Array\<string\> | null、参照画像の**絶対パス**の配列)
  - `num_last_images_to_include` (integer | null)
  - **`model` / `quality` / `size` / `background` / `output_format` / `mask` に相当する引数は存在しない**。
    これらのAPI設定はCodex CLI経由では直接指定できず、自然文で希望を伝えることしかできない。
    「指定した」ではなく「自然文で依頼した」と記録し、実際に適用されたかは出力を確認してから報告する
- 画像生成モデルの内部名は、ツール定義・応答・ログのいずれからも取得できない。**「取得不可」と記録し、
  出力の見た目から推測しない**
- wrapperの `-Model` は Codex (テキスト) モデルの選択であり、画像モデルの選択ではない

### 2026-07-10 時点の実測 (codex-cli 0.144.0、旧記録)

- 5行程度の要件からCodexが constraints / avoid 込みの詳細プロンプトを自動構築し、生成に成功した
  (出力 1254×1254 PNG、1.85MB)
- 自然言語の3点変更指示 (時間帯・髪型・服装) による編集で、同一性・構図・ポーズを維持した編集が
  一発で成功した
- 編集は `referenced_image_paths` + プロンプトで発動した。wrapper の `-Attachment` は不要
  (仕様書にリポジトリ内のファイルパスを書くだけで、Codex が自分で画像を読み参照する)
- 出力はPNGバイナリの直接ファイル書き出し (`-SandboxMode workspace-write` が必須)
- これらは0.144.0時点の記録であり、0.154.0でも同様に動くかは個別に確認すること
  (ツール定義自体は0.154.0でも生成・編集・参照画像パスの3引数構成を確認済み)

## 2. 生成タスクで渡す要件

[推奨] 以下を、依頼内容に必要な範囲で記載する。未指定項目をすべてユーザーへ質問する必要はない。

- **用途**: ゲーム素材、挿絵、バナー、UI用画像など
- **保存先・形式**: 成果物のリポジトリ内パスと必要な形式
- **内容・スタイル**: 被写体、動作、画風、色など
- **必須の構図条件**: 縦横比、全身／上半身、配置、余白、見切れの禁止など
- **背景・透過**: 背景を描くか、透明素材にするか
- **文字**: 必要な文字列、配置、出現回数。不要ならその旨
- **避けたい要素**: 不要な人物、小物、文字、ロゴなど
- **検収条件**: 何を満たしたら完成とするか

ユーザーが指定した条件と、AIが補完してよい項目を区別する。指定のない装飾、写実化、背景、小物を
「品質向上」の名目で追加しない。

プロンプトの長文化自体を目的にしない。要件を満たす具体的な説明を優先する。

### 生成タスクの例

```text
用途：2Dゲームのキャラクター選択画面に使う立ち絵。
出力：assets/characters/mechanic.png
形式：透過PNG。
内容：作業着を着た整備士。手に工具を1本持つ。
スタイル：アニメ調の線画とセル塗り。
必須条件：
- 全身と足先を含める。
- キャラクターを中央に配置し、四辺に余白を残す。
- 文字、ロゴ、背景の風景は追加しない。
補完してよい項目：
- 指定に矛盾しない範囲で、配色と細部を決めてよい。
検収：
- 画像を開いて内容を確認する。
- 実際に透明画素が存在することを確認する。
- 足先、工具、髪が画面外へ切れていないことを確認する。
```

## 3. プロンプト形式

[公式/API] 短文、説明文、タグ、JSON風の構造など、形式自体に唯一の正解はない
(公式ガイド: 「short prompts, descriptive paragraphs, JSON-like structures, instructions, and tags
can all express the same intent」)。要件が最も読みやすく更新しやすい形式を選ぶ、とされている。

[推奨] AIが読み直して要件を把握しやすい形式を選ぶ。複雑な依頼では「内容／構図／スタイル／制約」の
ように整理する。

`masterpiece`、`8k` などの品質語を重ねるだけで、必要な構図や細部の説明を代替しない。「高品質」より
「線の太さを一定にする」「人物の足先まで入れる」のような観察可能な条件を優先する。

[公式/API] カメラやレンズの指定は見た目を誘導する表現として扱い、物理的に厳密な再現を保証するもの
とは扱わない (公式ガイド: 「treat camera specifications as cues for appearance, not a guarantee of
exact physical simulation」)。

[推奨] 1プロンプトへの詰め込みすぎを避け、ベースを作ってから小さな変更で反復する。

## 4. 透明背景

[公式/API] GPT Image 2.5では透明背景をサポートする。APIを直接使う場合は `background: "transparent"`
と、`output_format: "png"` または `"webp"` を指定する (JPEGでは透明背景は使えない)。
`output_compression` はJPEG/WebPの圧縮率指定であり、PNGには使わない。

[準公式] openai/codex 組込みの imagegen skill は、現在は「built-in `image_gen` に本物の透明背景を
依頼し、アルファチャンネルをそのまま保持させる」という方針を案内している。旧版にあった
「クロマキー色で生成してからローカルで色抜きする」回避策の記載はなくなっており、本文書もその回避策を
一律のルールとしては採用しない。同スキルは、built-in `image_gen` に出力先パスの引数があるかのように
記述・依存しないことも注意点として挙げている。

[CLI実測 2026-09-19] Codex CLI 0.154.0 の `image_gen.imagegen` へ自然文で透過を要求し、実際の
アルファ透過を持つ PNG が得られた (1回目は不成功、2回目で成功)。編集経路でも入力の透過は維持された。
被写体の alpha は 253〜254 で 255 の画素が無く、外周に alpha 1〜63 の薄い暈しが残る。
「alpha=255 の画素があること」を検収条件にしない。詳細は末尾の「実測記録」節。

[推奨] Codex CLI経由では、公開されたツール仕様と動作結果に基づいて利用可否を判断する。自然文では
「実際のアルファ透過を持つPNG。白背景や市松模様を描かない」と要件を伝える。

出力後は次を確認する。

- 画像に透明度情報があり、実際に透明画素が存在する
- 市松模様が画像に描き込まれていない
- 背景だけでなく被写体まで消えていない
- 髪、細い線、影、半透明部分、輪郭に不自然な欠けや色残りがない
  (公式ガイドもデコード後のアルファチャンネルを髪・ガラス・影・輪郭まで含めて確認するよう案内している)

直接透過出力が利用できない場合は、単色背景からの背景除去を代替手段として検討する。その際は被写体に
含まれない背景色を選び、輪郭への色の混入を確認する。直接生成と後処理のどちらで透過を実現したかを
報告する。

## 5. 編集タスクの基本

[推奨] 編集指示は、次の5項目で組み立てる。

1. **編集元**: 今回変更する画像のパス
2. **変更点**: 何を、どこまで変えるか
3. **保持条件**: 変えてはいけない重要な特徴
4. **参照画像**: 参照がある場合、その役割
5. **出力・検収**: 保存先と確認する条件

保持条件は具体的に書くが、変更指示と矛盾する属性を列挙しない。髪型を変更する依頼で「髪の形を完全に
保持する」と指示しない。

顔立ち、衣装の形状、線画、色、構図など、タスク上重要な条件を優先する。2D素材では、写実的な質感や
陰影を自動で追加しない。

[公式/API] 公式プロンプトガイドは、編集では「change only X」のように変更対象を限定し、同一性・
ジオメトリ・レイアウト・照明・ラベルなど維持したい詳細を列挙するよう案内している。除外したい要素
(不要なテキスト・ロゴ・透かし等) も明示する。「same style as before」のような参照表現は文脈を
運べるが、結果がドリフトした場合は重要な制約を再度書き直すべきとしている。

### 編集例

```text
編集元：assets/characters/mechanic_original.png
出力：assets/characters/mechanic_navy.png

変更：
- 上着の色だけを紺色へ変更する。

保持：
- 顔立ち、表情、髪型、ポーズ、工具、構図を維持する。
- 上着の形状、縫い目、線画、元の陰影表現を維持する。
- 元の2Dセル塗りを維持し、写実的な質感を加えない。
- 背景の透過を維持する。

検収：
- 上着が指定色になっていること。
- 上着以外に意図しない変化がないこと。
- 元画像を上書きしていないこと。
```

## 6. 反復編集

[公式/API] `previous_response_id` や画像ID参照によって会話状態を利用する編集経路 (Responses API、
`action` パラメータ `auto`/`generate`/`edit`) は存在するが、反復編集でも保持対象に変化が生じることが
ある。公式ガイドも、直前の出力を次の編集入力として渡し、1回につき1つの変更を依頼し、保持したい詳細を
毎回再掲するよう案内している。

[推奨] 呼び出し経路による暗黙の引き継ぎに依存せず、各回の編集元画像と重要な保持条件を明示する。

通常は採用済みの直前の出力を次の入力とする。不採用の結果をそのまま編集し続けない。顔立ちや線画などの
変化が蓄積した場合は、採用済み画像または原画像へ戻り、必要な変更を整理して再編集する。

一度の編集では、原因と結果を確認しやすい範囲に変更点を絞る。生成後は変更点だけでなく保持対象も
比較する。

[CLI実測 2026-09-19] 2回の連続編集で、変更点 (キャップ追加、ブーツ黒化) は反映されたが、1回目で
変更対象外の色 (つなぎ) が変わり、2回目で下端の余白が失われた。保持条件を毎回全列挙しても防げて
いない。採用済み画像を入力にする運用と、出力後の保持対象の比較は省略しない。

### 見た目の保持とピクセル単位の保持

[推奨] 「同じ顔立ちに見える」「構図が維持される」と、変更対象外の画素が完全に一致することは異なる。

[公式/API] 公式ガイドも、ある領域をピクセル単位で完全に維持する必要がある場合は、プロンプトだけに
頼らず、承認した編集結果を元画像へ合成するよう案内している。

完全一致が必要な領域は、プロンプトだけで保証しない。必要に応じて、承認した編集領域を原画像へ合成し、
対象外の画素が変化していないことを差分で確認する。

マスクを指定できる経路でも、指定外領域の完全一致が保証されるとは仮定しない。

## 7. 複数参照画像

[公式/API] 公式ガイドは、各入力を番号と役割 (被写体・スタイル・衣装・背景など) で識別し、どう組み合わ
せるか、どの要素がどこへ移るかを説明するよう案内している。

各入力に **インデックスと役割** を付けて参照する:

```text
Image 1: 編集対象。顔立ち、ポーズ、構図を採用する。
Image 2: 衣装の形状と配色だけを参照する。人物の顔、体型、ポーズ、背景は採用しない。
競合する場合、人物の同一性と構図はImage 1を優先する。
```

[推奨] 各参照画像について「何を採用するか」「何を採用しないか」を必要に応じて指定する。参照は必要な
ものに絞る。枚数を増やすだけで同一性や品質が向上するとは扱わない。

[公式/API] APIの `images/edit` は、複数画像入力について「同じ形式・同じサイズで、かつ各50MB未満」で
あることを要求する。これはAPI固有の制約であり、Codex CLIやwrapperにも共通する上限として記載しない。
マスクを使う場合、マスクは編集対象画像と同じ形式・サイズで、アルファチャンネルを含む必要がある。

## 8. 画像内文字

[推奨] 文字列は引用符で囲み、配置、役割、出現回数を指定する。例:「『整備中』を上部に1回だけ表示する。
ほかの文字は追加しない」。

[公式/API] 公式ガイドは、必要な文言を引用符で囲んで位置や書体を説明すること、見慣れない単語やブランド
名は1文字ずつスペルアウトすること、余計な文字を出力しないよう依頼したうえで出力のスペルと可読性を
確認することを案内している。旧版 cookbook の定型句 `Render this text verbatim. No extra characters.
No duplicate text.` はそのまま使える。

生成後は、誤字、脱字、重複、不要な文字、読みづらい配置を確認する。OCRを使う場合も、OCR結果だけで
正しいと断定せず、必要に応じて目視確認する。

誤りがある場合、文字の大きさや配置、余白、指定可能な品質設定を調整する。必要な文章を、ユーザーに
無断で省略・変更しない。

正確な文字組みが必須で生成だけでは満たせない場合は、画像と文字を分けて作成し、後から文字を配置する
方法を検討する。

## 9. サイズと品質

[公式/API] GPT Image 2.5では `low` / `medium` / `high` / `xhigh` / `max` / `auto` の品質設定があり、
両モデルとも既定値は `auto`。公式ガイドは「小さな文字、情報密度の高い画像、複数フォントが混在する
場合は medium または high を比較検討する」と案内している。

[公式/API] サイズは推奨値として `1024x1024` / `1536x1024` / `1024x1536` があり、カスタムサイズ
`WIDTHxHEIGHT` も指定できる。カスタムサイズの制約: 幅・高さは16の倍数、アスペクト比は1:3〜3:1の範囲、
最大辺3840px、総画素数655,360〜8,294,400。出力形式は `png` (既定) / `jpeg` / `webp`、
`output_compression` はjpeg/webpで0〜100を指定できる。これらはAPI固有の数値であり、Codex CLI経由で
同じ数値が指定できるとは限らない。

[推奨] これらは対応する利用経路でのみ指定する。最高設定を常に使用せず、要件を満たす品質と処理時間の
バランスで選ぶ。

比較時は、最初にプロンプト、参照画像、寸法、形式、共通して指定できる品質設定をそろえる。その後、
一度に一つの条件を変更する。同じ品質ラベルでも、モデル間で品質や処理時間が同じとは限らない。

タスク仕様書では、希望の縦横比と必要な納品寸法を区別する。厳密な寸法が必要なら、実際の出力寸法を
確認する。

生成後のリサイズやトリミングが必要な場合、許容範囲を確認し、縦横比の変形や重要部分の切り落としを
避ける。後処理した場合はその内容を報告する。

## 10. 検収

### ファイル確認と内容確認

[推奨] magic bytesはファイル形式の確認であり、生成成功や内容の正しさを保証しない。

検収は次の順に行う。

1. **ファイル**: 保存先、形式、デコード可否、寸法を確認する
2. **生成内容**: 指定した被写体、スタイル、構図、文字、透過を確認する
3. **編集内容**: 指定変更の反映と、保持対象への意図しない変更を比較する
4. **成果物管理**: 元画像の保持、変更ファイル一覧、gitの実態を照合する

実体確認は **magic bytes** で行う: PNGは先頭8バイトが `89 50 4E 47 0D 0A 1A 0A`
(`head -c 8 file.png | od -An -tx1`)。`file` コマンドでも可。

生成物は `codex-verify check` に **untracked binary** (`?? path/to/image.png`) として出る。
**枚数・ファイル名が事前に不明でも検収は機能する**。検収は期待値照合型ではなく差分検出型
(snapshotとの比較) なので、clean treeガードが効いていれば「実行後に存在する新規ファイル = すべて
Codexの成果物」と帰属できる。ストーリーボードから自由に複数枚生成させる場合も、Codexの自己申告
リストとgit実態の照合はそのまま機能する。

gitベースの検収は変更の把握に使い、画像の内容が要件を満たすかは別途検収する。

ただし **出力先はリポジトリ内の1ディレクトリに縛る** こと (名前・枚数は自由でよい)。リポジトリ外
(%TEMP% 等) への書き出しはgitベースの検収に映らない盲点になる。

多枚数の場合、形式・デコード・寸法などの機械的確認は全数実施する。内容をサンプリング確認した場合は、
その範囲を報告し、未確認の画像まで確認済みとしない。

ファイル容量が極端に小さい場合は確認のきっかけにはなるが、容量だけでプレースホルダーや失敗と
判定しない。単純なアイコンや透過素材は正常でも小容量になり得る。画像を開き、寸法と内容を確認する。

## 11. 既知の注意点

- **Windowsの旧版不具合**: codex 0.120〜0.123 で Windows/WSL の image_gen tool が利用不可になる
  不具合が報告されていた (openai/codex issues #19133, #21640)。さらにネイティブ Windows で
  **エラーを出さずプレースホルダー PNG を黙って生成する** ケースの報告もある。0.144.0 (2026-07-10)
  および 0.154.0 (2026-09-19、ツール定義の確認のみ) では、少なくとも feature flag・tool定義は正常。
  古い codex で失敗する場合や、生成物が不自然に小さい/単色の場合は、まず `codex --version` と
  プレースホルダー疑いを確認する
- 日本語パス問題は wrapper (`-C` 指定 + ASCIIパス前提) の既存ガードがそのまま適用される。
  `codex exec` 呼び出し時は ASCII パス (`/tmp` 等) を指定する

## 実測記録 (2026-09-19 E2E)

[CLI実測] codex-cli 0.154.0、Windows 11 ネイティブ、ChatGPT アカウント認証。`/codex-implement` 経由
(`-SandboxMode workspace-write`、`-Model` 未指定)。検収は `codex-verify` + Python 標準ライブラリによる
PNG デコード (alpha 計測) + 目視。詳細は `docs/worklogs/2026-09-19-issue-44-image-gen-2.5-e2e.md`。

| ケース | 結果 | 要点 |
|---|---|---|
| 透明背景の2D素材 (生成) | 合格 (2回目で透過取得) | 1024×1536 RGBA、alpha=0 が 70.7%。被写体は alpha 253〜254 で **255 の画素は無し**。外周に alpha 1〜63 の薄い暈しが 1.8%。上下の余白は 8〜16px と極薄 |
| 日本語文字入り画像 (生成) | 合格 (1回) | 「整備中」「午後3時まで」各1回、誤字・余計な文字なし |
| キャラクターの色変更 (編集) | 合格 (1回) | つなぎのみ紺色化。顔・線画・構図・透過を維持 |
| 複数参照による衣装変更 (生成+編集) | 合格 (各1回) | Image 2 の衣装のみ反映。Image 1 の同一性・ポーズ・小物を維持し、Image 2 の人物は混入なし |
| 連続編集 (編集×2) | 変更点は反映、保持対象にドリフト | 1回目で指示外の色変化 (つなぎが濃紺→明るい青)、2回目で下端余白が 0 に。保持条件を毎回全列挙しても防げず |

観察: 出力先・形式・サイズ・品質・透過はいずれもツール引数に無く、Codex は prompt 内の自然文で伝えて
生成後に指定パスへ配置した。画像モデル名は全ケースで「取得不可」。
